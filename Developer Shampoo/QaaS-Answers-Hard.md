## Q21. Policy chains

A policy is a runtime object that can initialize itself, make a decision or apply pacing, and delegate to the next policy. `Policy` holds `Next`, an ordering `Index`, abstract `SetupThis`/`RunThis`, and public `Add`, `SetupChain`, and `RunChain`. `SetupChain` initializes the current policy and every successor. `RunChain` catches `StopActionException` from the current policy and returns false; otherwise it delegates, eventually returning true. Unrelated exceptions are not converted into an ordinary stop. This is a concrete Chain of Responsibility, with the Boolean representing whether the action may continue according to the chain. [Policy](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Policies/Policy.cs#L5) is the base implementation.

`Add` inserts according to ascending index and returns the possibly new head. Callers must keep that return value. If a lower-index policy is inserted ahead of the current head and the caller discards the result, the variable still refers to the old head. Recursing through `Next` handles longer chains; equal-index policies retain insertion order under the current algorithm. `CountPolicy` and `TimeoutPolicy` have index zero. The current `LoadBalancePolicy` index is `int.MaxValue`, and increasing/advanced policies inherit that value. The repository prose describing indices one and two is stale. The operative principle—limits ahead of pacing—is supported by the code, but the actual numeric values matter when extending the system.

`PolicyBuilder` is a cloneable configuration holder. `Configure(IPolicyConfig)` resets its alternatives and assigns the selected concrete family through a typed switch. Its fluent With methods call that operation; calling WithCount followed by WithTimeout on one builder replaces the selected family rather than building a two-policy chain. `Build` rejects missing or conflicting alternatives and creates one policy. `BuildPolicies` takes an array of builders, builds each, and combines them using the returned head from `Add`; null or an empty array yields no chain. Multiple policies therefore require multiple builders or explicit runtime composition. [Configure](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Policies/PolicyBuilder.cs#L41) and [BuildPolicies](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Policies/PolicyBuilder.cs#L195) make this explicit.

Count policy resets its counter to zero, increments on each `RunThis`, and throws when the counter reaches or exceeds the configured maximum. Timeout policy restarts a stopwatch during setup and stops when elapsed time reaches its duration. Fixed load balance computes a message interval from rate/time interval, waits for the next slot, adjusts pacing, and restarts the interval timer. Its waiting code uses sleeping plus a short spin near the boundary, rather than a pure busy loop. Increasing load balance changes the target rate over time. Advanced load balance moves through configured stages with count/time criteria and applies each stage's rate; its final stage remains active instead of indexing past the array or automatically terminating the whole action. A separate count/timeout can bound the action.

An author-written composition example uses verified constructors:

```csharp
Policy chain = new CountPolicy(100);
chain = chain.Add(new TimeoutPolicy(5_000));
chain = chain.Add(new LoadBalancePolicy(rate: 20, intervalMs: 1_000));
chain.SetupChain();

// Pseudocode: this placement models a post-operation check.
do
{
    PerformOneOperation();
} while (chain.RunChain());
```

`PerformOneOperation` is intentionally pseudocode. Placement matters more than the visual loop shape. Runner's publisher sends and records an item before calling `RunChain`; a false result is then translated to `StopActionException` to stop further iteration. Count 100 therefore observes 100 completed checks in that sequential path; a hypothetical pre-check loop would have different boundary behavior. Consumer and transaction callsites must be inspected separately, especially no-message reads and batch operations. It is not valid to derive exact delivery count solely from `CountPolicy`'s name or to assume one policy invocation corresponds to one low-level message in every action family. [Publisher policy callsite](https://github.com/TheSmokeTeam/QaaS.Runner/blob/0b184ee3c9f6111bc6aca070f0c6f9c9bfd8283f/QaaS.Runner.Sessions/Actions/Publishers/Publisher.cs#L51) demonstrates the post-send check.

Timeout is likewise checked where the action invokes the chain; it does not itself cancel a currently blocked network call. A transport timeout, cancellation token, and policy timeout can be related but remain separate mechanisms. Under parallel action execution, work may already be scheduled or in flight when a policy stops future iteration. The policy objects contain mutable counters/timers without a universal concurrency abstraction around each `RunChain`; a reader should inspect the action's scheduling and synchronization before promising an exact concurrent cap. A semaphore around I/O limits concurrent I/O, not automatically atomic access to every policy field. Stopping is a cooperative decision at a callsite, not rollback of completed sends.

Boundary checks should cover zero/one counts and the actual call placement; timeout exactly at the threshold using the available timer abstractions where possible; insertion of a new minimum-index head; three-plus chain members; equal indices; null/empty chains; advanced stages with amount, time, and neither; final-stage persistence; and work already started in parallel. The inferred rationale for ordering hard limits first is avoiding unnecessary pacing once a stop is known. Chain of Responsibility explains composition, Strategy explains the interchangeable rules, and Builder separates their settings from runtime counters. [Microsoft Stopwatch documentation](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.stopwatch) provides the elapsed-time foundation; QaaS source and Runner callsites determine the policy semantics.

One way to review a proposed policy is to write its state transition before discussing its configuration syntax. Identify what setup resets, which successful or unsuccessful operation advances the state, the exact comparison that stops work, and which exception represents that stop. For a count policy, “count messages” is incomplete until the action callsite establishes whether a no-message read, one batch, or a completed send advances the counter. For a pacing policy, distinguish intended start spacing from guaranteed end-to-end throughput: a slow external service may dominate elapsed time regardless of the configured rate. These questions expose assumptions that a builder-only test cannot detect.

Composition adds another boundary. A low-index limit can stop the chain before a later pacing rule executes; a pacing rule cannot retroactively undo an operation already completed by the action. Reusing one initialized policy instance across unrelated actions would also couple their mutable state unless ownership is deliberately designed for sharing. Consequently, a review should follow construction through the action field and setup call, then follow every RunChain call. **Design rationale, inferred:** runtime policy objects keep frequently updated counters and timers separate from reusable configuration descriptions. That separation makes rebuilding an action comprehensible, but it is not proof that copying a builder clones an already-running policy or that the runtime object can safely be shared among workers. Those are separate lifecycle and concurrency guarantees requiring evidence.

## Q22. Configuration ownership and mutation

“Configuration objects are internal” is an overgeneralization. QaaS uses several visibility choices: a class can be internal; a public builder can expose public getters with internal setters; some configuration types remain public for fluent construction; and friend assemblies can access selected internal APIs. `DataSourceBuilder`, for example, is a public class whose `Name`, `Generator`, and other configuration properties have internal setters, while public methods such as `Named` and `HookNamed` mutate them deliberately. Its assembly grants internals to specified consumers. Visibility should therefore be explained by exact declarations, not by the presence of Configuration in a namespace. [DataSourceBuilder visibility](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.SDK/DataSourceObjects/DataSourceBuilder.cs#L21) is a representative example.

The observable purpose is to offer controlled builder operations while preserving a binding/materialization surface for trusted framework consumers. Reflection-based binding can populate nonpublic members when configured to do so. This does not mean the members are public source-level APIs for arbitrary callers, and `InternalsVisibleTo` is an assembly-level compile-time accessibility decision, not a security sandbox. The design benefit of limiting accidental setter coupling is a reasonable inference; it should not be inflated into a guarantee that no external code can ever inspect or mutate state.

Typed and object-shaped patches deliberately differ. `UpdateConfiguration<T>(current, incomingTyped)` returns the incoming value when current is null or when runtime types differ. For equal runtime types it uses partial merge semantics: values matching a fresh default instance are treated as omitted. This preserves existing values when a caller constructs a mostly empty typed patch, but makes “set it explicitly to the default” ambiguous. In the merge helper, null patch values preserve existing values, and empty patch lists do not clear an existing list. A nonempty list is replaced rather than appended. A typed patch is thus not equivalent to replacing the entire configuration or applying every property verbatim.

The object-shaped overload is appropriate when presence itself carries meaning. An anonymous object naming only `Host` should leave other fields alone; an explicitly named null clears the existing flattened value. Indexed paths cause conflicting list prefixes to be removed before overlay, preventing stale trailing elements from an older list. Ancestor/descendant conflicts are normalized so a scalar and child object do not coexist at one path. There is a further subtlety: clearing a configuration key and rebinding can cause a nonnull constructor default to reappear in the C# object. “Explicit null clears the stored key” is accurate; “every property becomes null regardless of its initializer” is not. [Object-shaped updates](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Configurations/ConfigurationUpdateExtensions.cs#L88) and [Typed merging](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Configurations/ConfigurationBindingUtils/ConfigurationMergeUtils.cs#L42) show the difference.

The following author-written C# sketch uses a deliberately simple nullable default; it has not been compiled as part of this answer:

```csharp
public sealed class EndpointOptions
{
    public string? Host { get; set; }
    public int Retries { get; set; } = 3;
}
var original = new EndpointOptions { Host = "staging", Retries = 9 };
var typed = original.UpdateConfiguration(new EndpointOptions { Host = "prod" });
// Retries=3 in the fresh patch is treated as omitted; existing 9 is preserved.
var explicitPatch = original.UpdateConfiguration((object)new { Retries = 3 });
var cleared = original.UpdateConfiguration((object)new { Host = (string?)null });
```

These are semantic examples, not a guarantee that every overload always creates a new instance. The typed update has fallbacks that merge into the current object when constructor constraints prevent ordinary materialization. The method's return value must be used and aliasing considered. Changing a polymorphic configuration's runtime type replaces the incoming configuration instead of merging incompatible members. An object-shaped patch cannot infer an implementation for a missing interface-typed configuration; the method throws rather than inventing a concrete type.

Cloning addresses a different problem: making reusable builder variants independent before applying changes. Framework's `ICloneable<T>` documents isolation of state the builder itself mutates while allowing external resources to be shared. `BuilderCloner.DeepClone` uses a reference-equality visited map, preventing recursion cycles and preserving repeated-reference relationships in the clone. It rebuilds one-dimensional arrays, lists, dictionaries, and hash sets, then otherwise uses `MemberwiseClone` and recursively copies fields across base classes. Primitive/known immutable or opaque values—including strings, types, reflection metadata, assemblies, and delegates—are shared. This is Prototype behavior, not serialization-based cloning.

The implementation has boundaries that should be understood rather than hidden behind “deep.” Dictionary values are cloned but keys are reused, and rebuilt dictionaries/hash sets use default construction rather than preserving every custom comparer. Opaque delegates are shared and can close over mutable external state. `ContextBuilder.Clone` specifically replaces the cloned configuration-builder container with a fresh one seeded with the original sources/properties, because its build operation appends sources. That isolates the collection container while source/property objects may remain shared. Resource-bearing builders need deliberate custom cloning when generic field recursion is inappropriate. [BuilderCloner](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.Infrastructure/BuilderCloner.cs#L33) and [ContextBuilder.Clone](https://github.com/TheSmokeTeam/QaaS.Framework/blob/daa83a2b7ddcba5142760fc42833486219efd1ba/QaaS.Framework.SDK/ContextObjects/ContextBuilder.cs#L22) document these mechanisms.

Focused checks should clone a template, mutate a nested child configuration and collection in one branch, and verify the original/other branch. Add a repeated-reference graph and cycle, a custom comparer, a captured delegate, typed default versus object explicit-default patches, null clearing, and shorter list replacement. These target observable isolation requirements rather than asserting all references differ. Builder and Prototype patterns help explain the API, while [Microsoft access-modifier documentation](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/classes-and-structs/access-modifiers) supplies the language background. The source establishes behavior; the reasons for every historical visibility choice remain partly inferred.

Suppose a reusable builder contains a list of endpoints, and one case needs only the first endpoint. A nonempty typed patch can replace the list, while an empty typed list may be interpreted as omitted and preserve the original list. An object-shaped indexed patch handles stale trailing entries by clearing conflicting prefixes before overlay. Those differences are observable API semantics, so a customization layer must choose its patch form deliberately rather than describing both overloads as ordinary assignment. The returned configuration is the value to carry forward into the next build step.

Clone and update should also be evaluated in sequence. Cloning first may isolate a mutable nested builder, but a shared delegate can still close over an external list used by both variants. Updating one cloned builder then changes only its copied fields while later delegate execution can observe that shared external list. This is not a contradiction in the cloner's behavior; it is a boundary between builder-owned mutable state and opaque resources deliberately retained by reference. A realistic independence test should mutate the specific state the intended scenario owns and inspect observable behavior, rather than asserting that every object reference in two graphs differs.

## Q23. Dependency injection and ownership

Dependency injection in QaaS is the mechanism that supplies shared execution services and discovered hooks to runtime collaborators. It is not a claim that every object is created by the container. Runner's ExecutionBuilder directly constructs many configuration/runtime objects and passes already-built collections into resolved logic constructors. The builder is the place to distinguish container registrations, explicit constructor calls, manually supplied resolve parameters, and plugin creation. Treating all of them as “Autofac magic” prevents an accurate lifetime analysis.

The Runner builder has a root container and creates a dedicated child lifetime scope for the build. Within that child scope it registers the same Context object under `InternalContext` and `Context`, using RegisterInstance and SingleInstance. Therefore a logic requiring InternalContext and a hook requiring Context see two service views of the same object. The narrower type is an API boundary, not a second independent execution. A `ByNameObjectCreator` registration provides name-based implementation discovery. Hook-data registrations describe configured assertion/generator/probe invocations, including the configured instance name, implementation type identifier, and configuration section. Loader modules or the specialized probe path turn those records into the lists that builders request.

```text
Conceptual ownership map, not complete registration syntax:
ExecutionBuilder root container
  child build scope
    one context object -> services Context and InternalContext
    name-based object creator
    configured hook records -> hook instances/list services
    DataSourceLogic / SessionLogic / StorageLogic / ...
Execution receives child scope on successful Build
Execution.Dispose -> child scope.Dispose
```

The phrase SingleInstance must be interpreted relative to registration ownership. Registering an instance in a child scope does not make it a process-global singleton shared by unrelated executions. Autofac's documentation distinguishes the scope in which a service is shared from its lifetime/disposal ownership. In this code, the execution context is deliberately introduced at the child build scope. A parent service cannot safely acquire arbitrary child state as though it were globally available. Conversely, a long-lived owner retaining a short-lived execution service can keep invalid or stale state beyond the intended execution boundary. [Autofac's lifetime guide](https://docs.autofac.org/en/latest/lifetime/) explains those general sharing/disposal rules.

The current source registers orchestration logic types and resolves them after constructing runtime collections. For example, SessionLogic receives the built `List<ISession>` using a TypedParameter, while its context is resolved from the scope. AssertionLogic receives its assertion list, and StorageLogic receives both storage list and execution type. This is a pragmatic mixture of explicit construction and DI. It is useful because the collections are configuration products, while shared context and creation services have a scope-oriented role. That explanation is inferred from the wiring; the behavior itself is directly visible in Build.

Hook lifetimes need additional care. A named hook entry identifies a configured invocation, not merely a reusable implementation type. Loading configuration mutates hook state, and hooks may retain context, attachments, counters, or generated data. Caching one instance across executions can therefore mix configuration or evidence even when both executions use the same CLR class. Specialized probe loading also has execution-context concerns; it should not be flattened into a generic claim that all hook objects are constructed identically. The framework provider/module implementation and Runner probe-loading code establish the actual creation path.

Disposal responsibility is explicit in Runner: Build transfers the child scope into Execution, and the catch branch disposes it if construction fails. Runner's cleanup publishes ReportPortal results before disposing execution scopes. A correctly scoped service must remain available until its last consumer finishes. However, container disposal only covers objects the container actually owns/tracks under its registration rules. It does not prove that an arbitrary manually created protocol object is released unless the relevant action or owner disposes it. Session cleanup separately disposes actions and collectors, demonstrating that multiple resource boundaries coexist.

Mocker creates a child scope in LoadContextScopeDependencies and registers Context/InternalContext plus generator and processor hook data. Those hook-data services explicitly use InstancePerLifetimeScope. Yet the constructed Mocker Execution does not receive the child scope, and its Dispose method is empty. That is the limit of what these files prove: there is per-build scope creation, but not the same demonstrated ownership transfer as Runner. An exam answer should identify the gap rather than promising automatic cleanup. Similarly, separate scopes do not make a user's static mutable fields safe.

A useful audit introduces a disposable test dependency and two differently configured executions, records which context each hook observes, and verifies intended disposal ordering. Another test forces construction failure after scope creation and checks cleanup. The inferred architectural goal is isolated units of work with reusable construction rules; the practical review asks whether every dependency's owner and last use are visible. DI reduces wiring duplication, but it does not replace reasoning about resource ownership, mutable state, or concurrency.

For a concrete identity check, resolve Context and InternalContext from the same build scope and compare object references. The expected relationship is one shared object exposed through two types, not two copies synchronized by the container. A hook writing allowed shared context state and a logic reading that state are therefore interacting through the same instance. This helps explain both the convenience of the arrangement and the need to control mutation: registering two service types does not create a concurrency boundary between them.

For a concrete ownership check, follow a protocol from its factory call to the action field that retains it and the action's cleanup path. If that object was directly constructed, a lifetime diagram containing only Autofac scopes is incomplete. Conversely, a disposable service actually resolved and owned by a scope should not be manually disposed prematurely while reporting still needs it. Ownership questions are answered by creation, registration, transfer, and final use together. No single annotation such as SingleInstance proves all four.

This distinction also matters when reviewing a proposed singleton optimization. Reusing cached discovery metadata is relatively different from reusing a configured hook that holds execution Context. Before promoting a service's lifetime, list its mutable fields and references to case-specific collaborators. If any outlive their intended execution, separate scopes elsewhere will not repair the retained reference. The current builder/provider split gives concrete places to inspect that risk without assuming that every cached object is unsafe or that every scoped object is automatically safe.

## Q24. Runner-to-Mocker control

The control plane is a request/response protocol layered on Redis, separate from the application's HTTP/gRPC/socket traffic. Runner represents a control operation as a MockerCommand action. Mocker Controller subscribes handlers, decodes requests, updates or reads server state, and publishes responses. The shared `Qaas.Mocker.CommunicationObjects` assembly contains the DTOs and naming helpers that keep both sides consistent. Notice the `Qaas` namespace spelling: substituting a guessed namespace or duplicating a channel string can break integration even when the conceptual design is correct.

Runner's command runtime creates a Redis connection, selects the configured database, generates a command correlation ID, and stores timeout/retry settings. Command execution first discovers instances using ping channels for the configured server name. It subscribes to ping responses, publishes requests, and records discovered server-instance identities. If none are found, it throws rather than silently reporting success. Once instances are known, it dispatches commands and verifies that the expected instances returned successful responses. The runtime maintains response state under a lock and uses snapshots when examining discovered/successful/failed responses.

Channel construction belongs to CommunicationMethods. Requests use `runner-to-mocker:{contentType}` and responses use `mocker-to-runner:{contentType}`, with optional server and instance segments appended and lowercased. Ping discovery targets the server-level channel, while command handling can target an instance. The helper also constructs input/output consumer endpoint names for evidence exchange. These actual strings supersede old prose mentioning a `qaas:mocker:` prefix. They should be generated by the shared helper, not copied into unrelated code where spelling and casing can diverge.

```text
Illustrative control sequence, not direct Redis commands:
Runner subscribe ping replies -> ping server name
Mocker instances -> replies containing instance identities
Runner subscribe command replies -> ChangeActionStub(action, stub, id)
Mocker handler -> validate payload -> serverState.ChangeActionStub
Mocker -> CommandResponse(id, instance, command, status)
Runner verify expected replies -> continue scenario
Later Consume -> capture/drain evidence -> Runner data exchange
```

The shared CommandType enumeration has ChangeActionStub, TriggerAction, and Consume. Ping is a separate request/response protocol, and Status is an outcome field/enum, not an additional command kind. CommandRequest combines its command discriminator with the corresponding optional payload. CommandHandler validates required payloads and important names, calls the appropriate server-state operation, and catches operation exceptions into a failed CommandResponse with exception information. BaseHandler performs JSON deserialization, delegates handling, and publishes the response. Its deserializer tolerates property casing and string-enum forms. Malformed/empty messages can be logged and ignored, so a caller needs timeout behavior for missing responses.

Consume illustrates why acknowledgement timing matters. The handler uses Interlocked.CompareExchange to permit one active consume lifecycle. It configures cache capture and drains relevant input/output streams into Redis, with cleanup in a finally path. Its synchronous bridge waits for that lifecycle so the response reflects completion or failure of the drain rather than merely successful task scheduling. Duplicate in-flight Consume requests return from the command operation without starting another drain; that is not a general exactly-once command ledger. TriggerAction can invoke behavior, while ChangeActionStub changes active response selection; their retry safety must be considered according to their effects.

Redis Pub/Sub does not inherently persist missed messages for offline subscribers and uses at-most-once delivery semantics. Therefore subscription ordering, response correlation, deadlines, and retries are essential application responsibilities. A retry after a missing response cannot prove the original operation did not happen: the request may have executed while its acknowledgement was lost. It is unsafe to claim exactly-once execution merely because a request has an ID. The learner should inspect whether each handler actually deduplicates IDs before proposing retry guarantees. [Redis's official Pub/Sub documentation](https://redis.io/docs/latest/develop/pubsub/) describes the underlying delivery model.

The four identities answer different questions: ExecutionId organizes Runner context, server name identifies the logical mock target, server-instance ID identifies a discovered runtime, and command ID correlates one exchange. A reliable scenario logs them distinctly, checks every expected instance's response, and treats incomplete discovery or failed acknowledgements as actionable failures. When a command handles evidence, Runner performs its additional data exchange and places retrieved inputs/outputs into its live and final communication data. That makes mock evidence available through the same session/assertion model as other action results.

Command explains explicit operation messages; Facade describes the server-state control interface hiding transport-specific state; Producer-Consumer explains cache capture and draining. The inferred rationale is dynamic scenario control without restarting the mock host. A meaningful integration test drops or delays one response, duplicates a Consume request, sends a missing payload, and verifies correlation, single-inflight behavior, cleanup, and Runner failure reporting. Such a test evaluates real protocol guarantees instead of assuming that Redis connectivity alone proves the control scenario is reliable.

Timeout analysis must include the controller's actual consume loop. `ConsumeAsync` uses an inactivity stopwatch and restarts it after every successful push to the Redis list. Its timeout is therefore a quiet-period limit, not a fixed maximum duration for the entire command. A steady stream can keep the drain alive beyond the configured interval. Input and output drains are launched according to InputOutputState and joined together, so completion also depends on which streams are active. A Runner acknowledgement deadline shorter than a busy consume lifecycle can expire while Mocker is still doing useful work. The scenario must coordinate these different deadlines rather than assume they denote the same clock.

For example, with a one-second inactivity interval, messages arriving every half-second can repeatedly reset that timer. After traffic stops, the drain needs its remaining quiet interval before acknowledging completion. This illustrates the code's behavior; it is not a recommendation for those particular numbers. To validate it deterministically, record push times and response time, introduce a known quiet period, and verify capture is disabled afterward even when a Redis write fails. Also preserve action-name casing when selecting cache capture: route/control lookups and cache filtering need not share one comparer. A command that successfully finds an action does not prove a differently cased cache filter will collect its evidence; [TransactionsCache](https://github.com/TheSmokeTeam/QaaS.Mocker/blob/c3aa787b2db6d4c796b0ec6625af16799150e5ec/QaaS.Mocker.Servers/Caches/TransactionsCache.cs#L21) uses a case-sensitive string comparison. **Design rationale, inferred:** the inactivity window accommodates bursty traffic, while the finally cleanup and single-active lifecycle protect a temporary capture operation rather than providing general command deduplication.

## Q25. Tasks and failure propagation

Task usage in QaaS spans genuine asynchronous delays, worker-thread scheduling of synchronous actions, aggregate coordination, and synchronous bridges at public orchestration boundaries. These uses are not equivalent. `Session.RunAsync` awaits delays and the collection of action/collector tasks. `SessionExtensions.CreateTaskFromAction` uses Task.Run around the synchronous `action.Act()` call. That allows concurrent action execution but does not transform a blocking protocol operation into nonblocking I/O. A worker can remain occupied inside a synchronous receive, semaphore wait, or sleep. Performance and cancellation analysis must follow the operation inside the task, not just the presence of an async return type.

At the session layer, actions are started through Stage.RunAsync and their tasks are accumulated. As explained in Q17, action-stage starts are ordered, but Stage does not await all actions before returning. Session awaits the full action collection, then launches collectors and awaits them separately. SessionLogic starts sessions via ISession.RunAsync; its own synchronous Run method uses GetAwaiter().GetResult when materializing stage results and deferred sessions. Session.Run is also a synchronous bridge to RunAsync. The code therefore deliberately exposes mixed sync/async boundaries despite older guidance that can sound like a blanket prohibition on every blocking wait.

The action wrapper is a major exception boundary. It captures the action type/name, invokes Act in Task.Run, and returns a tuple of the action and its internal communication result. If Act throws, the wrapper looks up the live session, cancels matching input/output communication token sources, normalizes/appends an ActionFailure, and returns null. OperationCanceledException receives a cancellation-specific message. Thus a failed action often becomes recorded evidence rather than a faulted task that aborts the entire session. Final materialization skips absent tuple data while retaining normalized failures in SessionData.

```text
Pseudocode of the action failure boundary:
Task.Run:
    try: return (action, action.Act())
    catch error:
        cancel live streams associated with this action
        record normalized ActionFailure
        return null
    finally: log action completion
```

That boundary is not universal exception suppression. Errors during session initialization, stage orchestration, collector setup, result materialization, source selection, or other code outside the wrapper may still escape. An assertion hook has its own catch region that maps hook exceptions to Broken, while selection outside that region can still fail. `Parallel.ForEach` can surface aggregate exceptions, and policy-stop handling must be assessed at the actual catch location. A correct audit names each boundary instead of asserting that all exceptions automatically become one common result type.

Live consumers require both normal-completion and failure signals. On successful transaction completion, CompleteAdding tells a blocking collection that no new data will arrive. On failure, cancellation sources associated with the failed action are cancelled. Consumers must observe the token/collection contract to stop correctly; cancelling a token source does not forcibly terminate arbitrary user code or interrupt every blocking external call. Disposal is different again: it releases owned resources after use, but is not a substitute for requesting cancellation and joining outstanding work. These distinctions are essential for avoiding hangs in tests that depend on live output.

Session's finally block attempts to dispose task objects, actions, and collectors and removes its running-session entry. The disposal helper logs failures and continues, so one disposal failure does not necessarily prevent later cleanup attempts there. Runner has a separate cleanup pipeline: publish ReportPortal results, dispose executions, teardown, then dispose the runner. It records cleanup exceptions while continuing remaining steps and can rethrow or aggregate them afterward. Runner Execution.Dispose releases its owned Autofac scope. Therefore cleanup failures are observable and should not be described as always harmless or swallowed.

Mocker uses LongRunning tasks for server and controller lifetimes; CompositeServer does the same for children and waits for any child to stop. This scheduling hint suits synchronous long-lived listeners but does not implement cooperative shutdown. Mocker Execution.Dispose is empty, and local-run return does not visibly cancel the tasks. A stopped/faulted composite member causes an exception, but sibling termination is not established by that code. This asymmetry is an important current implementation limit rather than a reason to invent a graceful-stop contract.

A focused failure-path test should create an action that exports a live stream then throws, plus a dependent consumer that observes cancellation. Assert the dependent operation stops within a bounded test deadline, the session retains an ActionFailure, the running-session entry is removed, and actions are disposed once. Separately force a ReportPortal cleanup failure and confirm later cleanup steps still run. These are proposed tests, not claims of execution in this research. The inferred rationale behind the task/wrapper design is concurrency with diagnosable failures and best-effort cleanup; the audit determines where that intent is implemented and where lifecycle work remains incomplete.

A timeline clarifies why cancellation and disposal are separate obligations. First an action exports live communication collections. Next another action begins consuming them. The producer then fails before normal completion. The wrapper cancels the associated tokens and records a failure, but the dependent operation can stop only if it observes the relevant token or collection contract. After tasks have reached an appropriate completion boundary, the session attempts resource disposal and removes its live-session entry. Moving disposal earlier could race active code; omitting a completion/cancellation signal could leave readers waiting. The correctness claim is about this sequence of events, not about having a finally block somewhere in the method.

Exception timing deserves the same precision. A synchronous exception thrown while creating a Task is different from an exception stored in a Task that faults later. A try/catch around a call returning Task cannot catch that later failure unless the task is awaited or synchronously observed inside the protected region. This matters when evaluating retry helpers as well as session orchestration: a synchronous retry wrapper around an asynchronous storage operation does not automatically retry faults delivered after task creation. Trace the await location and retry delegate type before making such a claim. **Design rationale, inferred:** QaaS retains synchronous protocol and facade boundaries while using Tasks for overlap and coordination. This reduces the need to redesign every existing interface, but callers must explicitly reason about scheduling, observation, cancellation, and ownership at each bridge.

## Q26. Parallelism and shared-state invariants

QaaS has several independent concurrency layers, so a single `Parallelism` setting is not a global limit for the whole process. Runner starts its built executions sequentially, while MockerRunner starts executions concurrently. Within Runner, sessions in one session stage can overlap; deferred sessions can continue across later stages until their RunUntilStage barrier. Within a session, action tasks start by ordered action stage, but completion is joined after all stages have launched. Within some actions, many data items can be processed concurrently. Assertions also execute with Parallel.ForEach. Mocker transport hosts may process multiple requests, and CompositeServer starts several listeners concurrently. Each layer has its own ownership and synchronization concerns.

For transactions, the iterator alone does not implement the configured limit. `IterableSerializableDataIterator.ApplyToAll` chooses plain Parallel.ForEach or ordinary foreach according to a boolean. Transaction constructs a SemaphoreSlim when parallelism is configured and waits/releases it around the transactor call. The protected region is the external `Transact` operation, not every part of source enumeration, serialization, result logging, deserialization, or policy evaluation. Consequently, proving at most N concurrent transactor calls does not prove at most N worker tasks or at most N simultaneous operations anywhere in the action. Publishers must be inspected in their own implementation rather than assuming identical critical sections.

Parallel transaction mode materializes the indexed serialized sequence before workers execute. The code comment explains that this permits safe indexing into retained original data. Sequential mode remains streaming to preserve lazy-generator behavior. This is a real memory/latency tradeoff: a large or unbounded source cannot be reasoned about as though the parallel path consumes one item at a time forever. Materialization also means serialization/source exceptions may occur before any protocol call in that batch. Iterator is the relevant pattern, but laziness is a property of a particular path, not a universal guarantee attached to the interface name.

```text
Pseudocode of the actual parallel transaction structure:
indexed = serializedItems.Select((item, index) => (item, index))
if parallel configured: indexed = indexed.ToList()
Parallel.ForEach(indexed, item => {
    wait semaphore
    try: reply = transactor.Transact(item)
    finally: release semaphore
    capture original input and reply using matching index
    run policy chain
})
```

Result lists are protected with locks when the transaction appends input/output records. Live blocking collections and queues provide their own concurrent operations. The session failure bag is concurrent, and live-session dictionary helpers use a shared lock for lookups/updates/removal. These mechanisms protect specific operations, not every compound invariant. For example, two separately locked input/output appends do not make the two lists an atomic paired transaction. Under out-of-order completion, list positions can differ. Matching indexes identify related evidence more reliably than positional zipping, but repeated iterations and filtering still require inspection of index scope and metadata preservation.

Policy evaluation is particularly subtle. Transaction calls RunChain after the protocol call and evidence logging, and throws StopActionException when the policy returns false. It catches StopActionException around the iterator invocation. In sequential mode that direct exception reaches the catch. In parallel mode, exceptions from worker delegates can be wrapped by Parallel.ForEach into AggregateException; the iterator does not normalize them. Therefore a claim that policy stopping is guaranteed graceful and equivalent in parallel mode is not proved by this code. Already-running work may also complete after another worker decides to stop. A learner should flag this as a test/fix concern rather than silently rewriting the behavior into an ideal cancellation algorithm.

Consider two requests A and B with B returning first, while a policy decides to stop after one completion. The semaphore can limit in-flight protocol calls, but both may already have entered. B's evidence may be appended first; A can still finish. No visible global rollback removes those results. The policy object itself may be shared among workers, so its counter/time/state implementation must be inspected for thread safety. A non-thread-safe hook or protocol object can race even when collection appends are protected. Immutable list containers passed to assertions likewise do not protect mutable fields inside session bodies or shared static state in hooks.

The inferred design rationale is throughput with reusable synchronous protocol contracts and live evidence exchange. The tradeoffs include thread-pool pressure, eager parallel enumeration, partial results, and complicated stop semantics. A meaningful adversarial test records current/max in-flight transactor calls with Interlocked, deliberately reverses response order, checks correlation metadata rather than list order, triggers a policy stop in sequential and parallel modes, and verifies live-stream completion/cancellation. A separate multi-session test checks when deferred evidence becomes visible. These tests would establish the specific invariants; they should not be replaced by a blanket statement that SemaphoreSlim or Task automatically makes the system thread-safe.

A useful concurrency invariant has a subject, scope, and observation point. “Parallelism is three” is vague; “at most three calls are simultaneously inside this transaction's transactor method” can be measured. Increment an atomic active counter on entry, update the observed maximum safely, and decrement in a finally block. Place the instrumentation inside the fake transactor rather than around the whole action, because the semaphore protects a narrower region. Run the same scenario with two independent transaction actions to show why their limits do not automatically combine into one process-wide cap. This is a proposed deterministic test design, not a claim that the current code supplies that instrumentation.

Result correlation requires another invariant. Give every generated item a stable business identifier, retain it in expected data, and arrange for replies to finish in reverse order. Compare evidence using identifiers and the recorded matching metadata, while checking the scope of indexes across iterations. A passing test that sorts both collections without preserving duplicates may hide a missing item, so also compare counts and multiplicity. Finally, make one worker fail while another remains active and inspect which partial records survive and how the wrapper marks failure. **Design rationale, inferred:** the implementation favors throughput and traceable evidence over preserving arrival order. That choice is defensible only when downstream assertions use explicit correlation and treat partial completion as observable evidence rather than silently equating concurrent lists with a sequential transcript.

## Q27. Choosing an extension boundary

The synthetic-record requirement belongs to a generator hook because it produces domain input data. It does not require adding a transport to Framework. Start from the current SDK contract rather than an invented universal `BaseHook<T>` abstraction. `BaseGenerator<TConfiguration>` implements the hook configuration/context behavior and leaves `Generate` abstract. The current implementation binds configuration with the QaaS binder, validates it recursively, and returns the validation-results collection; an empty collection is a normal successful result. The name lookup and instance preparation are separate responsibilities in Providers and the consuming builder.

The following is a proposed teaching implementation using the actual generic base and method signature. It is a new example, not a quotation of an existing Common generator. It compiled successfully in an isolated net10.0 project against the current SDK source at `daa83a2b7ddcba5142760fc42833486219efd1ba` (zero errors; two existing BinaryFormatter warnings in the referenced Serialization project). Recompile against the exact SDK package version selected for a production consumer; a source-reference build does not establish compatibility with every published package.

```csharp
using System.Collections.Immutable;
using System.ComponentModel.DataAnnotations;
using QaaS.Framework.SDK.DataSourceObjects;
using QaaS.Framework.SDK.Hooks.Generator;
using QaaS.Framework.SDK.Session.DataObjects;
using QaaS.Framework.SDK.Session.SessionDataObjects;

public sealed record LabelledConfig
{
    [Range(1, 1000)] public int Count { get; set; } = 3;
    [Required] public string Prefix { get; set; } = "sample";
}

public sealed class LabelledGenerator : BaseGenerator<LabelledConfig>
{
    public override IEnumerable<Data<object>> Generate(
        IImmutableList<SessionData> sessions,
        IImmutableList<DataSource> sources)
    {
        for (int i = 0; i < Configuration.Count; i++)
            yield return new Data<object>
            {
                Body = new { Id = i, Label = $"{Configuration.Prefix}-{i}" }
            };
    }
}
```

This implementation deliberately keeps no mutable counter on the generator instance. The iteration variable belongs to each enumerator, making repeated enumeration easier to reason about. Nevertheless, iterator execution is deferred: changing `Configuration` between obtaining and enumerating the sequence changes what the sequence observes. If the product promises a snapshot, copy the relevant values before returning a separately implemented iterator and test that promise. Similarly, inspect data-source enumeration/caching and action-policy behavior before assuming this hook's `Count` is the only control on how many items an action receives. The point is to define ownership and evaluation timing, not to declare every iterator intrinsically thread-safe.

A complementary assertion should derive from the current `BaseAssertion<TConfiguration>` and implement `Assert(IImmutableList<SessionData>, IImmutableList<DataSource>)`. Its configuration should identify the relevant session/action or expected labels rather than scanning all captured traffic accidentally. It should report useful `AssertionMessage` and, when justified, trace or attachments. Define whether missing evidence is a failed expectation, a skipped scenario, or an execution error under the existing assertion engine's status mapping. Do not hard-code an assumed enum or status-to-exit-code mapping from stale docs; inspect Q19's source trail. A meaningful assertion checks the observable requirement, not merely that a generator returned three objects.

Test the hook in layers. A configuration test binds valid and invalid inputs and inspects validation results and unknown-key warnings. A generator test enumerates the result and verifies identifiers, labels, deterministic ordering, and count boundaries. A discovery test loads the built assembly through the actual provider path and resolves its qualified name. A collision test adds a same-short-name type to demonstrate why a fully qualified selection matters. An integration test places the generator behind the real DataSource/action path and confirms the serializer produces the intended payload. An assertion test supplies both correct and incorrect captured SessionData, including an empty input and an unrelated session. These tests catch distinct contracts; repeating a loop in the test would not.

Now change the requirement to a new transport. The domain generator and assertion can remain reusable because their contracts are transport-independent. The new transport must implement the relevant capabilities: sending, reading, transacting, fetching, or chunk operations. Do not give every interface Connect/Disconnect just because several existing protocols use that lifecycle. Add the compiled factory dispatch and configuration wiring appropriate to the selected action, plus serialization/metadata mapping and error handling. If Mocker must host this transport, implement the server-side integration too; a client protocol adapter is not automatically a mock server. Update schema generation, documentation, tests, packaging, and downstream references. This is the Type A hook versus compiled-core extension boundary discussed in Q1 and Q10.

The patterns have concrete roles. Plugin describes assembly-discovered hooks. Template Method describes the base class furnishing configuration behavior while the subclass supplies the operation, though the overall lifecycle is orchestrated externally rather than by one textbook template method. Strategy describes interchangeable generator/assertion behavior through a contract. Factory describes choosing and constructing a supported implementation; do not call every switch an Abstract Factory. Adapter describes translating the new transport's client API into QaaS capabilities and data envelopes. Iterator explains deferred generation. These labels help reason about change, but the answer earns credit for explaining the actual collaboration and limitations, not for attaching six pattern names to a class.

For this particular generator, define the acceptance contract before extending the sample. With Count equal to three and a fixed prefix, there should be exactly three generated bodies, with distinct identifiers and predictable labels. Invalid count configuration should be detected through the hook's normal load-and-validate path. The sample intentionally ignores sessions and other data sources; if a later version derives values from those inputs, its dependency selection and empty-input behavior become part of the contract. Adding that behavior is more than adding another loop: it changes when generation can run and what evidence it requires.

The discovery check should exercise a packaged consumer as well as direct construction. Instantiating LabelledGenerator with `new` demonstrates method behavior but bypasses assembly discovery, configured-name resolution, Context injection, and configuration loading. Conversely, successfully resolving the type does not prove that enumerating it produces the expected serialized request. Keeping those checks separate localizes failures: lookup errors point toward packaging and identity, validation errors toward configuration, and payload mismatches toward generation or serialization. **Design rationale for the proposed example:** a local iterator variable and bounded validated count make the smallest useful extension easier to reason about. They deliberately avoid adding shared caches, background tasks, or transport concerns before the requirement needs them, while leaving the same SDK boundary available for a richer implementation.

## Q28. Releasing a cross-project change

A source change has several independently versioned consequences. The runtime code, a built NuGet package, a restored downstream dependency, an editor schema, a generated reference page, and an offline documentation archive can describe different snapshots. Therefore a release plan must identify the owner and version of each artifact. “Merged to master” proves source availability at one repository; it does not prove that Runner, Mocker, templates, and the mirror have consumed the result. Resolved package references and artifact provenance make that distinction visible.

For an additive hook configuration property, begin in the owning Common package. Add or update the configuration member, its validation, implementation behavior, XML documentation, and tests. Decide how absence behaves and whether the new default preserves existing YAML behavior. Test both omission and explicit values, including invalid values. A change described as additive can still break users if its default changes output or previously accepted input becomes invalid. Then build and release the Common package under the repository's actual CI contract. Hook discovery itself should not require modifying Framework merely because the hook learns one more domain parameter. The consumer must nevertheless restore a package containing that implementation.

An SDK contract change has a larger impact. Enumerate all implementations and consumers in Framework, Common packages, Runner, Mocker, and user assemblies. A source-compatible-looking change can still affect already compiled assemblies, serialization assumptions, or hook discovery. Plan compatibility explicitly and apply semantic versioning to the actual published public contract. Do not claim every internal edit requires a major version: SemVer concerns incompatible public API changes. Build and test the downstream combinations that will actually ship, including a consumer assembled from packages rather than only project references. An unreleased local Framework project satisfying an API tells you nothing about an older NuGet dependency selected by Mocker.

PackageMirror consumes successful source CI `restored-packages` artifacts from its tracked repositories. The tracked list is narrower than “all repositories in the organization.” Its README documents stable-source-tag preference for most sources, with Runner treated differently. It preserves all currently used external dependency versions, but retains the latest allowed QaaS package version under its QaaS bucket and excludes specified non-distribution packages. Expired restore artifacts and saved state have documented fallback behavior. Review `state/` and the selected source runs rather than treating a workflow success as proof that every source is fresh. The mirror has both a fast push validation path and a manual full-sync path; pushing a source or mirror implementation change is not equivalent to publishing a full distribution.

```text
Source contract and tests
  -> built/published source package + successful restore artifact
  -> downstream compatible restore/build/test
  -> mirror selected source runs + package state
  -> runner-family / mocker-family schemas and hook catalogs
  -> refreshed CLI snapshots + source XML documentation
  -> deterministic generated references + strict docs validation
  -> qaas-docs CI offline archive -> mirror release copy
```

The family schemas include more than a single JSON schema file: `schema.json`, `docs-manifest.json`, and `hook-catalog.json` provide a stable contract for editors and documentation. Docs.Generator combines those mirror-owned inputs with committed CLI snapshots and source annotations. Public function documentation uses explicit `qaas-docs` placement metadata; documented extension methods with renderable XML can also receive inferred placement. A public method can therefore exist without appearing in curated generated references, but the absence of a placement tag alone does not prove an extension method is excluded. Fix missing documentation at its owning source or generation input; editing generated pages alone creates a change that regeneration overwrites. Refresh snapshots when CLI behavior changes, regenerate deterministically, and use drift checks plus a strict site build to validate the complete result.

The offline ZIM has a particularly important ownership boundary: qaas-docs CI builds it; PackageMirror downloads and republishes the existing bytes. Mirror does not become a second ZIM builder. A release plan should record where that archive came from and whether it matches the intended docs release. This is a pipeline pattern: each stage owns a transformation and an explicit output contract. Its benefit is auditability, but it also creates failure modes when one stage succeeds with stale inputs. A dependency graph alone cannot prove freshness.

`QaaS.Configuration` is a separate deployment-default package. Its `buildTransitive` target injects a module initializer; registration supplies fallback Elastic and ReportPortal defaults. Explicit runtime options/configuration retain precedence according to the consuming implementation. The repository describes public disabled/null defaults and an internal same-ID/same-version variant selected by the internal feed. That distribution policy means feed identity and cache state matter in addition to version strings. The mirror intentionally excludes that package from its normal public bootstrap archive. Teach this as the repository's deployment contract, not a general recommendation to publish different package contents under one public version.

For “runtime supports it but editor/docs do not,” first establish the actual loaded package version. Next compare family schema metadata, hook catalog contents, mirror state, CLI snapshot age, source placement tags, and generated outputs. A runtime binding test, schema validation, a docs drift check, and a package-only consumer test answer different questions. Approval should require the relevant combination and a recorded rollout order. The rationale for these checks follows the observed ownership boundaries; it is not an invented account of why every historical repository split occurred.

A practical release record can be small while still being precise: list the source commit, produced package identity, downstream resolved version, mirror source-run identity, schema/catalog generation input, and documentation build. For each item, identify the check that actually compares it with the intended change. This avoids a common circular argument in which a successful docs build proves only that old generated pages still compile, while a successful runtime build proves only that an older package remains usable. Freshness and correctness are separate properties of every artifact.

For the added hook setting, inspect the generated property description and the default shown to users, then exercise YAML with the setting omitted and explicitly supplied. If runtime behavior changes but generation inputs are stale, the fix belongs to the producing stage and its regeneration contract. If generation is correct but a consumer restores an old package, changing documentation cannot repair runtime behavior. **Design rationale, inferred:** explicit artifact ownership permits independent tooling and offline distribution, but demands provenance across boundaries. A defensible rollout names the compatibility window and fallback behavior; it does not rely on every repository moving to the newest commit simultaneously.

## Q29. Diagnosing misleading success

The observations do not establish one concurrency defect. A passed run, fewer captured replies, and an unexpected assertion-only result can arise at different phases, possibly from independent faults. Begin by preserving evidence: source/package versions, the exact command line, effective configuration, selected execution/session/action identities, logs, report outputs, storage location, and timestamps. Preserve the failing run's artifacts before another run overwrites a shared location. Then write down competing hypotheses and the evidence that would disprove each. “Tasks are unreliable” is not a falsifiable hypothesis until it specifies a missing await, shared state race, cancellation path, or scheduling assumption.

First verify the configured and materialized graph. Does the intended assertion exist after name/category selection? Does it receive the intended session data? A process that starts and exits successfully may not have exercised the business requirement. Introduce a deliberately failing assertion against a known input and verify that the failure appears in both the recorded result and the applicable exit behavior. If it does not, investigate selection or status propagation before instrumenting thread scheduling. Reporter success and assertion success are different observations; a publishing failure can be logged independently of a test failure.

Next isolate hook resolution. Two assemblies with the same simple type name can select an implementation according to the current provider's qualification and priority rules. Capture the resolved type's full name and assembly identity, not merely the YAML string. Re-run with a qualified name and the same inputs. If the mismatch disappears, that supports a discovery ambiguity; if the same implementation was already selected, the hypothesis is falsified. A minimal reproduction needs only two eligible types and one provider lookup, not a broker or full service deployment. Keep it independent from the concurrency experiment.

The copied configuration key requires a separate binding experiment. QaaS's custom binder does not necessarily behave like Microsoft's standard binder despite using a `BinderOptions` property with a familiar name. In the current source, the unknown-key path can log a warning and skip a member rather than throw. Therefore a misspelled or obsolete setting can leave a default in effect while the run continues. Compare the raw configuration, transformed root configuration, and resulting typed property. A focused test should assert both the resulting value and diagnostic behavior. Adding arbitrary delays will not repair an ignored count or selection setting.

For the reply-count problem, draw the actual scheduling timeline. Current Runner action stages start tasks and do not themselves impose a universal “all earlier actions finished” barrier. Session logic and session action-stage logic have distinct coordination rules. Verify the exact location where task collections are awaited, which work can overlap, and which count/timeout/policy causes an action to stop. Instrument item identity at generation, serialization, protocol invocation, response capture, and final session materialization. Compare generated count, attempted count, successful count, captured count, and assertion-visible count; these are not interchangeable metrics. Use a deterministic fake protocol to block/release chosen items so the race can be reproduced without network timing noise.

```text
Unexpected result
  -> Was the intended assertion selected and invoked?
  -> Did the expected hook type and effective configuration materialize?
  -> Did the input reach the protocol operation?
  -> Did the operation complete, stop by policy, fail, or remain pending?
  -> Was its result recorded in live and completed evidence?
  -> Did storage persist and restore that same execution/session evidence?
  -> Did reporting faithfully describe the assertion outcome?
```

Live-data readers introduce producer–consumer questions. Determine when the producer writes, when the consumer enumerates, and how completion is signaled. A concurrent collection protects specific collection operations; it does not make a multi-step check/enumerate/update sequence atomic, guarantee ordering, or deep-freeze payload objects. An immutable outer list similarly does not imply immutable objects inside it. The smallest reproduction should coordinate a writer and reader with explicit test synchronization and exercise completion and empty-input cases. Do not turn a flaky test into a slower flaky test by extending a sleep.

Finally, trace the assertion-only command through storage selection. Reusing a directory or object prefix can expose older data if identity or selection is wrong. Verify the artifact read, its provenance, and its session/action contents. Compare a full run with act-plus-assert for the same deterministic scenario; only the act path writes the saved evidence used by the assertion-only command. Then deliberately introduce stale evidence and prove the selector rejects or distinguishes it according to the actual implementation. If the store design lacks that guarantee, document the limitation and use isolated paths in the test; do not claim the execution ID magically namespaces every output. Finish with separate regression tests for each confirmed cause and one small integrated test for their interaction.

Organize the evidence ledger around one deterministic item that should have produced one reply. Record its generated identifier, the effective action name, the resolved protocol implementation, operation start/end, captured body and metadata, and the assertion's selected session. The first missing or changed representation narrows the investigation. If the item never reaches the transactor, response collection is not the first suspect. If the reply exists in final SessionData but the assertion does not see it, examine selection rather than the network. If both are correct in a full run but differ after restore, the storage path becomes the independent reproduction target.

Repeat only the minimum experiment needed to distinguish hypotheses. One run with qualified hook identity tests discovery; one run with a known typed property tests binding; one fake-protocol schedule tests overlap and stopping; one saved-artifact round trip tests persistence. Do not change concurrency, timeouts, storage locations, and assertions together and then attribute success to whichever change seems plausible. That produces a workaround without an explanation. **Diagnostic rationale:** the architecture contains explicit transformations, so a phase-local counterexample can identify a broken assumption without requiring every external service. Once a cause is confirmed, retain the smallest regression and add only the integration coverage needed to prove its interaction with the real runtime.

## Q30. Defending an end-to-end design

A defensible design starts with observable requirements and ownership boundaries. Suppose the service accepts an order, publishes an event, calls a downstream pricing service, and eventually stores a completion record. Runner owns test orchestration and evidence; the real service owns business processing; Mocker owns the configurable pricing response. Choose the supported protocols that match the real boundaries, and use named data sources, sessions, actions, and assertions so failures can be attributed. The architecture should state which external brokers/databases must exist and which components are replaced by Mocker. A diagram that silently mocks the very behavior under test cannot demonstrate that behavior.

Use one generator to create deterministic order identities and payloads, with configuration controlling a bounded scenario set. A processor returns the expected downstream body and protocol metadata. A baseline session exercises accepted orders; another scenario changes the mock behavior and checks a rejection or retry outcome. Probes capture useful environmental evidence, but assertions express the actual pass/fail conditions. Add consumers or collectors for the event and eventual record according to the appropriate protocol capability. A collector over historical data has different timing semantics from a live reader, and a transactor need not expose the same connection lifecycle as a sender. Those choices must follow the current interfaces rather than a generic “all transports connect, send, receive, disconnect” narrative.

This is a design sketch, not a claim that QaaS inserts all these barriers automatically. Define readiness and completion using observable conditions and the actual session/action scheduling semantics. Stage numbers alone are insufficient if the code launches tasks across action stages before awaiting completion. Select supported coordination mechanisms and test the timeline with blocked fake operations. A mid-test Mocker command must target the correct controller/action/stub identity and complete at a defined point relative to requests. A request already in flight may observe old state depending on the implementation; specify and test that boundary instead of promising a global instantaneous switch.

Build two independent execution configurations from an explicit baseline. Verify deep-clone behavior for the concrete mutable members you change, including collections and hook-specific configuration. Do not assume a clone recreates arbitrary resources or preserves every comparer. Execution IDs provide correlation, but isolation also depends on DI scope, shared dictionaries, static/provider caches, hook instance ownership, output paths, and external resource names. In an embedded host, use the returned-code Runner API so one run does not terminate the process. Dispose according to actual ownership and inspect Mocker's implemented cleanup rather than transferring Runner's lifecycle guarantees to it by analogy. Where cleanup is absent or incomplete, call it out as a limitation or a proposed improvement.

Data travels through several representations. Generated `Data<object>` carries body and metadata; serializers produce wire-compatible payloads; protocol adapters map metadata such as headers and routing information; captured communication data becomes session evidence; storage persists the representation required for later assertions. Verify whether metadata survives each transformation and whether null bodies and empty bodies remain distinguishable. The mock processor's response must satisfy the stub's actual serialization/output contract; it is not enough for a C# object to look plausible. Feature support must be tied to the actual restored package and implementation commit rather than inferred from a proposed change.

The failure matrix should include malformed configuration before work starts, a valid configuration selecting the wrong hook, a policy-controlled action stop, a protocol exception, a processor error, partial evidence, assertion failure, and reporter outage. For each, identify whether the implementation throws, records status, returns a code, logs and continues, or performs cleanup. Do not merge these into one universal error-handling claim. Persist enough evidence to reproduce the assertion phase without re-sending the business request. Give each execution a deliberate storage identity/path and retain package/configuration provenance. Use the act path to produce the stored artifact, then run assertion-only against that artifact. Compare its outcome with a full run of the same deterministic scenario; normal run does not call StorageLogic, so it is not itself the artifact-writing step.

All fifteen patterns can be defended concretely. Builder/Fluent assembles validated execution descriptions; Factory selects supported implementations; Strategy supplies interchangeable hooks, serializers, and reporting behavior; Template Method captures base lifecycle scaffolding; Adapter maps transport APIs; Composite is an analogy for nested execution/session/stage/action structure, with no claim of a uniform GoF component interface; Chain of Responsibility orders policies; DI/Composition Root wires ownership; Prototype motivates tested cloning; Iterator explains lazy data; Command represents CLI/control requests; Facade supplies Bootstrap; Pipeline describes data and release transformations; Producer–Consumer explains live evidence; Plugin describes reflection-discovered hooks. The student should also explain tradeoffs: flexibility introduces configuration ambiguity, concurrency requires ownership discipline, and separate artifact pipelines require provenance checks.

Verification should progress from unit tests for hook logic and validation to builder/discovery tests, deterministic scheduling tests, storage round-trip tests, actual local transport tests, and a small environment-backed end-to-end test. Mock-based tests prove dispatch and mapping under their assumptions; they do not prove HTTP framing, broker behavior, or server shutdown. Package-only smoke tests verify release compatibility. Schema/drift/site checks verify documentation distribution. This evidence matrix supports approval more strongly than one large green run. Proposed improvements—such as stronger readiness APIs or better cleanup—must be labelled proposals, with compatibility and rollout costs, rather than quietly inserted into the description of existing QaaS.

A final architecture defense should separate current guarantees from desired improvements in its acceptance criteria. For example, proving that a mock command returned a successful response establishes a control-plane observation; proving which in-flight business requests saw the new stub requires an additional experiment. Likewise, proving that an assertion-only invocation reads the expected stored evidence does not establish that all storage writes are retried after asynchronous faults. State those limits directly and propose targeted changes only where the requirement demands stronger guarantees. **Design rationale, inferred:** the ecosystem's separate contracts make individual boundaries inspectable and replaceable, but system-level reliability emerges from tested interactions between those boundaries rather than from any one pattern name.
